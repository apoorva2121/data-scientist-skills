# Decision log

## Stage 0 - Frame the problem - GATE PASSED
Considered: whether this is a ranking-under-capacity problem vs a plain classification problem.
Applied (fixed): primary metric = precision@10% (call capacity); secondary = average precision, recall@10%, lift, calibration.
Carried forward: n/a (framing stage)
Skipped: accuracy/plain ROC-AUC as primary - target is imbalanced (8.65% raw positive rate) and the action is capacity-capped, so a ranking-at-budget metric matches the business action better.
Evidence: problem_statement.md
Open risks: target window, prediction-moment timing, and success threshold are all ASSUMED (user unavailable). Time budget is 25 minutes total for the whole project - compact mode used throughout (fewer candidates, 5-fold CV, no repeats unless a screen is ambiguous, small search budget).

## Stage 1 - Structure audit + stateless cleaning - GATE PASSED
Considered: duplicates, sentinel codes, spelling variants, impossible values, ID columns, mixed units (column_audit.py flags).
Applied (fixed): drop 150 exact duplicate rows (6150->6000); contract_type: mapped 11 case/whitespace spelling variants to 3 canonical levels (Month-to-month/One year/Two year); total_charges: -999 sentinel -> NaN (360 rows, 9.0% of remaining); age: values >120 -> NaN (32 rows, one raw value was 250); customer_id kept as ID (unique key after dedup, 0 conflicting non-identical duplicates); signup_date parsed as date.
Carried forward: n/a (stateless only, non-negotiable #1)
Skipped: churn_reason, account_status_code cleaning - deferred to Stage 3 leak hunt (name and fill-pattern already suggestive of post-outcome fields, confirmed there rather than assumed here).
Evidence: code/01_clean.py, column_audit.csv, cleaning_log.md, cleaned.csv
Open risks: none of the removed/nulled rows concentrate in one class by construction (exact duplicate rows are identical copies of kept rows).

## Stage 2 - Validation design + carve test - GATE PASSED
Considered: stratified, random, group, time, group_time schemes.
Applied (fixed): stratified split (customer_id unique after dedup -> no group leakage risk; churn rate by signup-quarter cohort is flat at 6.8%-10.9% with no trend over 2023Q1-2025Q2 -> no strong evidence of drift requiring a time-based split). test=1200 (20%), holdout=900 (15%), train=3900 (65%), 5-fold CV on train, seed=42. Target rate preserved across all three parts (8.67%). Adversarial validation train-vs-test AUC = 0.4917 (near 0.5, confirms exchangeability, sanity check passed).
Carried forward: n/a
Skipped: group scheme - no repeating entity after dedup; time scheme - no evidence of drift in the only available date field (signup cohort), and no explicit "future period" deployment requirement from the user; kept as an open risk since the true prediction-moment timestamp is unknown (ASSUMED in problem_statement.md).
Evidence: code/02_split.md (make_split.py CLI run), split/split.csv, split/split_spec.json
Test-set precision estimate: primary metric is precision@10% (a proportion at n = top 10% of test = 120 rows); SE ~ sqrt(p(1-p)/120) - with an expected p around 0.25-0.40, SE is roughly 0.04-0.045, so a 95% interval of about +/-0.08-0.09 on the test set. This is wide relative to small model differences, which is why Stage 8 model selection uses CV, not the test set.
Noise floor: measured at Stage 7 in the primary metric's own units (precision@10%) using RepeatedStratifiedKFold(5,3) on a simple logistic-regression reference pipeline; recorded in search_space.json as noise_floor_sd (repeat_sd).
Open risks: no explicit "prediction moment" timestamp in the data; stratified/random split assumes rows are exchangeable across time, which the signup-cohort check supports but does not prove for the true scoring cadence.

## Stage 3 - Leakage hunt + relationship EDA (train only) - GATE PASSED
Considered: leak_screen.py univariate scores/flags on all non-ID columns; column-name heuristics (status, reason, result, final...); aggregate/window leaks (not applicable, no lookback aggregates were engineered); train/serving skew via adversarial validation.
Applied (fixed): DROP churn_reason (leak_screen score 1.0000, NEAR_PERFECT|DOMINANT|INFORMATIVE_MISSINGNESS; populated only for churned=1); DROP account_status_code (score 0.9949, NEAR_PERFECT|DOMINANT; 'C' status co-occurs with churned=1 93% of the time vs <0.1% for other statuses) - both read as post-outcome account state, not pre-churn attributes. These are fixed drops, never searched over (non-negotiable #4).
Carried forward: all remaining 10 features (tenure_months, contract_type, support_calls_90d, monthly_charges, total_charges, last_invoice_amount, signup_date/redundant, region, age, payment_method, avg_daily_usage_mb) pass to Stage 4-7 screening.
Skipped: dropping last_invoice_amount despite INFORMATIVE_MISSINGNESS flag and higher missingness for churned=1 (30.5% vs 16.4%) - its mean value tracks monthly_charges closely in both classes (no sign of an inflated post-cancellation final bill), so it is kept as a legitimate pre-churn feature with a missing indicator; logged as an open risk since the true recording time is unverifiable without the data owner.
Evidence: leak_screen.csv, leak_table.csv, code/02_leak_hunt.py
Adversarial validation (train vs test): ROC-AUC 0.4917 (near 0.5, as expected for a random stratified split).
Open risks: last_invoice_amount timing is ASSUMED, not confirmed with a data owner (user unavailable). account_status_code and churn_reason are dropped as leaks; if the retention team already has an operational process that flags customers the moment they enter a 'C'/cancellation status, that process (not a model) may already partially solve this problem - worth surfacing to the business.

## Stage 4-6 - Missing values, outliers, features - GATE PASSED (combined script, compact mode)
Considered (missing values): drop rows, median, median+indicator, KNN, iterative(MICE), native NaN (GBDT). Considered (outliers): none, winsorize p01/p99, log1p transform. Considered (features): derived ratios/date parts vs the raw columns already given.
Applied (fixed): none beyond Stage 1 sentinel/impossible-value nulling (no feature engineering step changed the data materially within the time budget).
Carried forward: median_indicator (both families) - proxy precision@10%: linear 0.2103 +/- 0.0358, within-noise vs winsorized variant 0.2077 +/- 0.0332 (diff 0.0026 less than corrected SE 0.0038, tied); native_nan (gbdt only) 0.1564 +/- 0.0278. outliers: "none" and "winsorize_p01_p99" both kept (tied, diff within corrected SE); log1p not screened (time budget - avg_daily_usage_mb extreme max, 73x p99, is a plausible real heavy-usage tail, not confirmed as an error, so aggressive transforms were deprioritized under compact mode).
Skipped: KNN/iterative imputation - only 2 numeric columns have any missingness (total_charges 9.95%, last_invoice_amount 18.0%) and both are weakly correlated with the rest of the feature set at this data size/time budget, so a simple median+indicator was judged sufficient rather than screened separately (time cut, logged per SKILL.md Stage-0 time-budget rule). New engineered features (tenure buckets, ratios) - not screened; tenure_months, contract_type and support_calls_90d already carry the dominant signal (leak_screen.csv scores 0.60-0.61) and the 25-minute budget was prioritized toward model/family search instead.
Evidence: code/03_screen_stages4to7.py, stage4_5_missing_outliers_screen.csv
Open risks: outlier handling for avg_daily_usage_mb was not deeply investigated; a handful of extreme values (up to 4196 vs p99 around 60) could be metering errors rather than real heavy users - flagged as a data-quality follow-up, not corrected here since it did not change the screened score beyond noise.

## Stage 7 - Baselines + model families + imbalance - GATE PASSED
Considered baselines: DummyClassifier(prior), business rule (month-to-month contract + support call volume, ranked), regularised logistic regression, DecisionTreeClassifier(max_depth=3). Considered families: regularised linear (logistic), LightGBM, CatBoost (both installed, CPU, under-5000-row band from ds-model-selection table). Considered imbalance strategies in order: metric+threshold at capacity, class_weight="balanced", resampling (SMOTE), balanced ensembles.
Applied (fixed): primary metric already fixed at Stage 0 (precision@10%, capacity-limited); class_weight="balanced" applied to all linear/gbdt candidates (order-of-preference step 2) rather than resampling, per ds-model-selection guidance that resampling rarely beats threshold/weighting for strong classifiers and harms calibration - not screened further given the time budget.
Carried forward: simple_logistic (0.2103 +/- 0.0358) kept as best baseline, within noise of business_rule (0.1897 +/- 0.0263, diff 0.0205 less than corrected SE 0.0358) but clearly above trivial (0.0846) and shallow_tree (0.1744, outside corrected SE); family screen: linear (0.2077 +/- 0.0332) beats lightgbm (0.1564 +/- 0.0278, diff -0.0513, magnitude greater than corrected SE 0.0219) and catboost (0.1679 +/- 0.0322, diff -0.0397, magnitude greater than corrected SE 0.0162) by more than the noise floor - both trees dropped from the family list.
Skipped: TabPFN/TabICL foundation models - not installed and installing is not permitted (compute rule); not requested from the user given the time-boxed run, logged as a next-step recommendation. Resampling (SMOTE) - order-of-preference step 1-2 (threshold+weighting) already met the objective; screening resampling too was cut for time.
Learnability verdict: LEARNABLE. Best family (linear) beats the trivial baseline (0.0846) by about 0.123, far beyond the noise floor (0.0133); learning curve for lightgbm shows a large train/validation gap (train 0.82-0.87 vs val 0.10-0.16) meaning variance-limited/overfitting for trees at this row count and feature count, consistent with the linear model win. Because the signal is real but partly variance-limited for trees and the current feature set is unlikely to explain all churn variance, more/better features (billing history depth, usage trend, complaint text, competitor offers) would likely help more than further model search.
Evidence: code/03_screen_stages4to7.py, stage7_baselines.csv, stage7_family_screen.csv, stage7_learning_curve.csv, search_space.json
Open risks: only default-ish hyperparameters were screened for LightGBM/CatBoost before Stage 8 tuning; Stage 8 joint search (30 Optuna trials) confirmed the tree families still lose to tuned linear, so this is not solely a default-hyperparameter artifact.

## Stage 8 - Joint pipeline search - GATE PASSED
Considered: every Stage 4-7 survivor as a categorical choice (missing_values: median_indicator/native_nan; outliers: none/winsorize; encoding: onehot only, target-encoding skipped for time given low-to-moderate categorical cardinality, max 20 levels for region) crossed with linear (C, class_weight=balanced) and gbdt=LightGBM (n_estimators, learning_rate, num_leaves, min_child_samples, subsample, colsample_bytree, reg_lambda, class_weight=balanced) hyperparameters, via Optuna TPE (multivariate, grouped) with MedianPruner.
Applied (fixed): 30 trials, 150s timeout, 2 seeds, top-3 finalists (compact-mode budget, well under the 60-trial/900s default in the joint_search.py template given the 25-minute project budget).
Carried forward/winner: T22 - linear, outliers=none, missing_values=median_indicator, encoding=onehot, C=0.01007, CV mean precision@10% = 0.2385 (best by mean AND the 1-SE pick - it dominates outright, no tie-break needed). Runner-up: same family with winsorized outliers, 0.2333 (within noise). Best gbdt trial: 0.2103, more than one corrected SE below the linear winner - dropped.
Locked-holdout check: winner refit on train, scored on the untouched holdout (900 rows): precision@10% = 0.2667, consistent with (in fact slightly above) the CV estimate of 0.2385 - no evidence the search overfit its own folds.
Skipped: CatBoost was not wired into the joint search's FAMILIES dict (only linear + LightGBM ported from the joint_search.py template) - it screened close to LightGBM and clearly behind linear at Stage 7, and adding its distinct hyperparameter API was not worth the remaining time budget.
Evidence: code/04_joint_search.py, search/trials.csv, search/finalists.csv, search/result.json
Open risks: 30 trials is a small search; a longer budget might tune LightGBM closer to linear, though the learning-curve variance-limited verdict at Stage 7 suggests more trials would help less than more data/features would.

## Stage 9 - Evaluation + sign-off - GATE PASSED
Final pipeline (Stage 8 winner) refit on train+holdout (4,800 rows), scored ONCE on the frozen 1,200-row test set (verify_test_untouched() returned True before scoring).
Test precision@10% (primary metric): 0.2583, 95% bootstrap CI [0.1917, 0.3250] (n_boot=2000, stratified resampling) - lift 2.98x over the test base rate of 8.67%.
Secondary: recall@10% 0.2981 [0.2212, 0.3750]; average precision (PR-AUC) 0.2140 [0.1693, 0.2916]; ROC-AUC 0.7186 [0.6695, 0.7702]; calibration ECE 0.3699, Brier 0.2226 (poorly calibrated - expected, since class_weight="balanced" distorts predicted probabilities per ds-model-selection guidance; not recalibrated within the time budget since the business action only needs a correct ranking for the top 10 percent, not calibrated probabilities - flagged as a limitation before probabilities are used for anything beyond ranking).
Sanity: shuffled-label check - real-label CV score 0.2385 vs shuffled-label 0.0821 (collapses to within noise of the test base rate 0.0867), confirming the signal is genuinely in the labels/features and not an artifact of row order or preprocessing.
Slices: contract_type - month-to-month customers rank far better (precision@10%-within-slice 0.2794) than one-year (0.0690) or two-year (0.0800) - expected, since month-to-month is both the largest slice and the dominant churn driver. tenure_bucket - newest customers (0-12mo) rank best (0.3478), longest-tenured (37mo+) worst (0.1017) - the model is better at flagging early-lifecycle risk than late-lifecycle risk. region - wide, mostly-overlapping-zero 95% CIs at n=43-71 per region; no region stands out as a reliable failure beyond sampling noise.
Evidence: code/05_final_eval.py, test_results.json, test_calibration.csv, test_slices.csv, feature_importance.csv, final_pipeline.joblib
Open risks: test set has only about 104 positives, so the CI on precision@10% is wide (roughly +/-0.07); region-level slice estimates are too small (n around 50-70) to certify fairness beyond noise - would need more data or pooling regions to check reliably.
